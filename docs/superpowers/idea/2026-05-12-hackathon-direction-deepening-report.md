# mtagent 赛题深化与明确方向报告

> 日期：2026-05-12  
> 状态：方向定稿 / 后续开发依据  
> 目标读者：项目成员、代码助手、产品调研同学  
> 赛题：美团 2026 AI Hackathon 赛题 05「现在就出发 · AI 本地路线智能规划」

## 1. 一句话方向

mtagent 不做泛泛的“AI 旅行攻略生成器”，而是做：

> 面向深圳、上海、西安的一日 / 半日本地即时路线规划助手，结合点评 POI、UGC 标签、用户偏好和真实路线服务，在 10 秒内生成可直接执行的个性化路线，并支持用户按“少排队、少走路、吃得好、拍照、亲子、情侣”等约束动态调整。

这个方向最贴赛题里的三个关键词：

- `本地路线智能规划`
- `直接可用、不踩雷`
- `多条件与个性化`

## 2. 当前已确认边界

### 2.1 城市范围

第一阶段只支持：

- 深圳
- 上海
- 西安

原因：

- 当前 mock POI 数据只覆盖这些城市。
- 赛题更看路线质量，不看城市数量。
- 每个城市都需要手工增强核心 POI 和区域规则，盲目扩城市会拉低可用性。

后续跑通后再扩城市。

### 2.2 场景范围

第一阶段主打：

- 半日路线
- 一日路线
- “现在就出发”的即时本地路线

多日旅行规划可以保留为扩展能力，但不要作为主线。

原因：

- 赛题名称强调“现在就出发”。
- 一日 / 半日更容易在 10 秒内生成稳定结果。
- 地图路线、排队、营业时间、当前位置等约束在短路线里更容易体现价值。

### 2.3 位置策略

支持两种方式：

```text
默认位置：
  用户没有输入当前位置时，系统默认城市中心 / 热门商圈 / 推荐起点。

手动位置：
  用户可以输入当前位置，例如“我现在在深圳湾公园附近”。
```

第一阶段不用强依赖浏览器定位权限，先支持文本输入位置即可。

### 2.4 偏好策略

偏好数据还没有完全做好，第一阶段采用：

```text
显式偏好：
  用户本次输入里说的偏好，例如少排队、想吃好、想拍照。

隐式偏好：
  从历史对话摘要里沉淀出的偏好，例如讨厌跨区、喜欢轻松路线。

默认偏好：
  用户没有说时，默认路线不要太累、不要频繁跨区、覆盖餐饮和至少一种游玩类型。
```

本次输入优先级最高，历史偏好只作为默认倾向。

## 3. 赛题要求拆解

赛题原文强调：

```text
用户需要将多个目的地串联成高效路线。
用户面临想吃好又不想排队、时间预算二选一等多重决策负担。
现有搜索和推荐需要用户反复筛选、自行组合。
系统需要结合 POI 数据、UGC 智慧和用户个性偏好。
自动生成可直接执行的个性化路线方案。
支持按时空、偏好等约束动态调整。
```

对应到 mtagent 的产品能力：

| 赛题要求 | mtagent 应该怎么体现 |
|---|---|
 串联多个 POI | 输出 3 个以上 POI，并有清晰顺序和路线 |
 高效路线 | 控制区域连续性、通勤时间、回头路 |
 想吃好又不想排队 | UGC 标签参与评分，处理约束冲突 |
 时间预算二选一 | 给出不同方案或明确取舍 |
 POI 数据 | 使用 mock 点评 POI 作为基础数据 |
 UGC 智慧 | 把评论/标签转成排队、拍照、亲子、性价比等结构化标签 |
 用户偏好 | persona、兴趣、节奏、历史偏好共同影响排序 |
 直接可执行 | 地图、时间段、交通段、停留时长、风险提示完整 |
 动态调整 | 支持换一个点、重排半天/一天 |

## 4. 评委关注点对应策略

赛题材料里的核心关注点包括：

- 完整性
- 创新性
- 应用效果

### 4.1 完整性

需要证明系统真的跑通了完整流程：

```text
用户输入
-> 意图解析
-> 候选 POI 构建
-> POI / UGC / 偏好评分
-> 路线组合
-> 地图展示
-> 用户反馈调整
-> 历史偏好沉淀
```

不能只展示一段漂亮文本。

### 4.2 创新性

建议主打 3 个创新点：

```text
1. 三层 POI 候选池
   城市必去 / 人群偏好 / 补位连接点。

2. 约束冲突可解释
   少排队、吃得好、少走路、想拍照之间有权衡，不是假装全都最优。

3. 局部动态调整
   用户不满意一个点时只换这个点，不整份路线重来。
```

### 4.3 应用效果

需要让评委相信路线真的能走：

- 10 秒内出结果。
- 至少 3 个 POI 串联。
- 至少覆盖餐饮 + 娱乐/文化两类。
- 地图路线不是假的直线。
- 路线有时间段、停留时长、交通时间。
- 用户能看到为什么这样安排。

## 5. 产品核心形态

### 5.1 用户输入

推荐支持这些输入字段：

```text
city: 深圳 / 上海 / 西安
time_window: 半日 / 一日 / 上午 / 下午 / 晚上
start_location: 可选，用户不填则默认
end_location: 可选
persona: 情侣 / 亲子 / 朋友 / 银发 / 独行 / 商务
interests: 拍照 / 美食 / 文化 / 购物 / 展览 / 自然 / 夜景
constraints: 少排队 / 少走路 / 预算有限 / 不要太累 / 不跨太远
must_visit: 用户指定必去点
avoid: 用户指定不想去 / 去过的点
```

自然语言输入可以被 Profiler 解析成这些结构。

### 5.2 系统输出

推荐输出：

```text
主方案：
  系统认为综合最优的一条路线。

备选方案 1：
  少排队 / 轻松版。

备选方案 2：
  兴趣优先版，例如美食优先 / 拍照优先。
```

每个方案包含：

```text
路线标题
适合人群
核心取舍
POI 顺序
每个 POI 的推荐理由
停留时长
交通方式和时间
路线风险提示
地图路线
可调整入口
```

## 6. POI 选择方向

### 6.1 结论

POI 选择质量主要靠：

```text
POI 数据标记 + 用户偏好结构化 + 约束评分
```

不是靠 LLM 自由发挥。

LLM 应该做：

- 理解用户输入。
- 解释为什么这么选。
- 在候选点之间做语义取舍。
- 根据用户反馈生成调整意图。

LLM 不应该做：

- 从全量 POI 里盲选。
- 判断真实交通路线。
- 直接控制地图绘制。
- 无约束重写整份路线。

### 6.2 三层 POI 候选池

#### 第一层：城市必去点

特点：

- 对第一次来的人高度相关。
- 不应该因为 persona 被过滤掉。
- 只因为时间、距离、预约、体力等因素调整安排方式。

例子：

```text
深圳：深圳湾公园、世界之窗、欢乐海岸、莲花山、华强北等
上海：外滩、豫园、陆家嘴、南京东路、武康路等
西安：钟楼、大雁塔、回民街、城墙、兵马俑等
```

关键规则：

```text
city_essential 不等于一定塞进路线。
它的含义是必须进入候选池，并获得较高基础权重。
```

#### 第二层：人群 / 兴趣偏好点

特点：

- 对某些 persona 或兴趣明显更适合。
- 用于生成差异化。

例子：

```text
情侣：拍照、氛围、夜景、精致餐厅
亲子：儿童友好、室内、休息方便、动线简单
银发：文化、低步行、交通方便、少排队
朋友：热闹、娱乐、夜生活、多人餐饮
独行：安全、好逛、轻量、咖啡/展览
```

#### 第三层：补位连接点

特点：

- 不一定是旅行目的本身。
- 负责让一天顺起来。

类型：

```text
餐饮
咖啡
商场
休息点
夜景
轻量活动
雨天备选
```

补位点非常重要，因为真实路线不是景点堆叠，而是：

```text
主锚点 -> 吃饭 -> 轻量逛 -> 休息 -> 夜景/返程
```

## 7. UGC 智慧方向

### 7.1 不要把 UGC 当长文本喂给模型

更推荐的方式是把 UGC 总结成结构化标签。

建议标签：

```text
queue_heavy: 排队久
photo_friendly: 适合拍照
family_friendly: 亲子友好
senior_friendly: 银发友好
couple_friendly: 适合约会
solo_friendly: 适合独行
quiet: 安静
lively: 热闹
good_value: 性价比高
premium: 价格高但体验好
rain_friendly: 雨天适合
night_friendly: 适合晚上
walk_heavy: 走路多
reservation_required: 需要预约
crowded_weekend: 周末拥挤
```

### 7.2 UGC 标签如何影响结果

例子 1：

```text
用户说：想吃好但不想排队

提高：
  rating 高
  food_quality 标签强
  queue_heavy=false
  路线顺路

降低：
  网红但排队久
  绕路
  周末拥挤
```

例子 2：

```text
用户说：情侣，想拍照，不想太累

提高：
  photo_friendly
  couple_friendly
  night_friendly
  同区或邻区

降低：
  walk_heavy
  queue_heavy
  跨远区
```

### 7.3 产品同学调研怎么接入

产品调研同学可以做：

- 小红书 / 大众点评 / 攻略样本收集。
- 总结不同人群的一日路线模式。
- 标注哪些 POI 是城市必去。
- 总结哪些路线让人觉得累。
- 总结哪些文案更容易让用户接受。

工程侧接收的不是长文，而是：

```text
route_templates
poi_manual_labels
ugc_tag_rules
bad_route_patterns
```

## 8. 路线规划方向

### 8.1 路线不是 POI 排序

路线规划至少要考虑：

- 地理位置
- 区域连续性
- 交通时间
- 营业时间
- 停留时长
- 排队风险
- 用户体力
- 餐饮时间
- 夜间适合度

### 8.2 区域连续性

大城市不能一味同区，也不能任意跨区。

推荐规则：

```text
同区：优先
邻区：允许
远区：只有 city_essential / must_visit / 强兴趣点才允许
一天跨区次数：默认 <= 1
回头路：高惩罚
稀疏区域：允许先去一个高价值 anchor，再接到邻近丰富区域
```

深圳例子：

```text
深圳湾公园 -> 世界之窗 -> 福田
可以接受，因为方向相对连贯。

宝安 -> 福田 -> 南山 -> 宝安
应该强烈惩罚，因为来回跳。
```

### 8.3 route_status 解释

虽然目标是使用真实路径，但真实路径服务可能失败。

因此每段路线都需要状态：

```text
real_route:
  真实路径成功，可以画实线。

estimated:
  没有完整路径，但有估算时间/距离，可以画虚线并标注估算。

unavailable:
  路线失败，不画两点直线，只提示路线暂不可用。
```

关键原则：

> 地图不能用两点直线伪装真实路线。

这会直接影响评委对“路线可用性”的判断。

## 9. 多方案策略

赛题提到“多维度最优路线方案”，建议不要只输出一个结果。

推荐输出 3 个方案：

```text
主方案：
  综合最优，平衡距离、兴趣、餐饮、体验。

少排队 / 轻松版：
  降低热门点、排队点、走路多的点。

兴趣优先版：
  根据用户偏好偏向美食 / 拍照 / 文化 / 购物。
```

每个方案要明确取舍：

```text
这条路线更少排队，但少覆盖一个热门地标。
这条路线更适合拍照，但晚餐时间会稍晚。
这条路线吃得更好，但预算略高。
```

这比只说“为你推荐最佳路线”更可信。

## 10. 动态调整方向

### 10.1 替换一个点

用户场景：

```text
我不喜欢这个景点。
我去过这里了。
这个地方太远。
这个餐厅排队太久。
```

系统行为：

```text
保持同一天 / 同一半天。
保持同一时间槽。
优先同区或邻区。
尽量保持同类角色。
避开用户明确不喜欢的 POI。
只重算相邻路线段。
```

### 10.2 重排半天 / 一天

用户场景：

```text
这半天太累了。
今天都不太喜欢。
我想改成美食为主。
我想少走路。
```

系统行为：

```text
只重排指定时间段。
其他方案保持稳定。
继承用户本次意图和历史偏好。
加入新的约束。
重新跑候选池和路线评分。
```

这是非常贴赛题“动态调整”的亮点。

## 11. 历史偏好方向

用户的想法是：

> 开启新对话时，整理上一次历史信息作为用户偏好，自动隐式注入到下一次 prompt。

这个方向是对的，但建议结构化存储，不要把上一轮全文塞进去。

推荐结构：

```json
{
  "likes": ["拍照", "轻松路线", "环境好的餐厅"],
  "dislikes": ["排队久", "跨区太多"],
  "pace": "relaxed",
  "budget_level": "medium",
  "recent_rejected_pois": ["世界之窗"],
  "last_city": "深圳",
  "notes": "用户更喜欢一日内区域连贯，不喜欢太赶。"
}
```

优先级：

```text
本次明确输入 > 本次隐含约束 > 历史偏好 > 默认偏好
```

风险：

- 历史偏好不能覆盖用户本次新需求。
- 用户偶然拒绝一个 POI，不一定代表永远讨厌同类 POI。
- 需要区分 dislike、been_there、temporary_avoid。

## 12. Agent 编排方向

第一阶段不要为了创新而拆很多 agent。建议保持清晰职责：

```text
Profiler
  解析用户输入，产出结构化 intent。

CandidateBuilder
  根据城市、时间、位置、偏好构建三层 POI 候选池。

Scorer / Planner
  对 POI 打分，组合路线，处理时间和区域连续性。

Critic
  检查重复、跨区过多、排队风险、营业时间、路线不可用。

Adjuster
  处理换一个点、重排半天/一天。

MemorySummarizer
  把历史对话沉淀成用户偏好摘要。
```

如果当前代码已经有 Profiler / Planner / Critic / Adjuster，就先沿用，不要大改架构。

最重要的是：

```text
Agent 边界要服务路线质量，而不是为了看起来复杂。
```

## 13. 推荐 MVP 版本

### P0：一日 / 半日主流程跑通

目标：

```text
输入自然语言
-> 解析意图
-> 生成一条 >= 3 POI 的路线
-> 包含餐饮 + 娱乐/文化至少两类
-> 10 秒内返回
```

验收：

- 深圳 / 上海 / 西安至少各有一个稳定 demo。
- 用户不输入当前位置时也能生成。
- 用户输入当前位置时能影响路线。

### P1：POI 三层候选池

目标：

```text
city_essential
persona_preferred
connector
```

验收：

- 城市核心地标不会被 persona 过滤掉。
- 餐饮 / 休息 / 夜景能作为补位点出现。
- 路线不只是景点堆叠。

### P2：UGC 标签评分

目标：

```text
queue_heavy
photo_friendly
family_friendly
walk_heavy
night_friendly
good_value
```

验收：

- “少排队”能明显避开排队重的点。
- “想拍照”能提高拍照点权重。
- “亲子”能提高亲子友好点权重。

### P3：多方案输出

目标：

```text
主方案
少排队 / 轻松版
兴趣优先版
```

验收：

- 三个方案不是同一条路线换文案。
- 每个方案有明确取舍说明。

### P4：地图路线可信

目标：

```text
真实路线画实线。
估算路线画虚线。
失败路线不画假直线。
```

验收：

- 没有重复路线。
- 没有两点直线伪装真实路线。
- 用户能看懂路线状态。

### P5：动态调整

目标：

```text
replace_stop
redo_day_or_half_day
```

验收：

- 换一个 POI 不影响整份路线。
- 重排半天 / 一天保留其他部分。
- 用户 rejected POI 不再回来。

### P6：历史偏好

目标：

```text
新对话自动注入历史偏好摘要。
```

验收：

- 用户上次说不喜欢排队，下次默认更偏少排队。
- 用户本次明确说“这次可以排队”，历史偏好会让位。

## 14. 推荐 Demo 剧本

### Demo 1：深圳半日即时出发

输入：

```text
我现在在深圳湾附近，下午半天，情侣，想拍照和吃饭，不想太累。
```

期望展示：

- Profiler 解析出 city、time_window、persona、interests、pace。
- 路线集中在南山 / 相邻区域。
- 包含拍照点、餐饮、轻量休息点。
- 地图路线真实可看。
- 给出少排队版和美食优先版。

### Demo 2：动态替换

用户说：

```text
我不想去世界之窗，换一个近一点的。
```

期望展示：

- 只替换这个 stop。
- 其他点不变。
- 重新计算相邻交通段。
- 用户 rejected POI 被记录。

### Demo 3：历史偏好

新对话输入：

```text
明天在上海安排一天。
```

系统自动参考历史：

```text
用户偏好轻松、拍照、少排队。
```

期望展示：

- 不需要用户重复说偏好。
- 路线默认更轻松。
- 说明“已参考你之前偏好的轻松节奏和少排队”。

## 15. 需要继续明确的问题

这些问题后续最好再定一下：

1. 每个城市是否先手工维护 20-40 个高质量核心 POI？
2. UGC 标签是从 mock 数据规则生成，还是产品同学先给一批人工标签？
3. 多方案是否都要画地图，还是第一阶段只画主方案？
4. 当前位置默认点每个城市用哪里？
5. 真实路线 API 失败时，前端具体怎么展示 `unavailable`？
6. 历史偏好是否按用户 cookie 存，还是只按本地会话存？
7. 10 秒内生成是否包含地图真实路线查询时间？

## 16. 最终方向判断

项目最应该强调的不是“会聊天”，而是：

```text
能理解用户目标
能把多个 POI 串成可执行路线
能处理偏好和约束冲突
能给出多方案和取舍解释
能让用户局部调整
能把历史偏好沉淀下来
```

第一阶段只要把深圳 / 上海 / 西安的一日半日路线做扎实，就已经比泛泛的旅游 AI 更贴赛题。

最终对外表达可以是：

> mtagent 用 LLM 理解用户，用点评 POI 和 UGC 标签筛选候选点，用区域连续性和路线服务保证可执行性，用用户反馈和历史偏好持续优化结果。它不是生成攻略，而是在帮用户完成一次“现在就出发”的本地路线决策。

## 1 · Context & Motivation

读完赛题 PPT 发现**硬约束红牌**：

```
赛题响应时间硬门槛: < 10 秒
v1.5 当前 wallclock: ~36 秒  ❌ 超 3.6x
v1.6 plan 目标:      ≤ 25 秒  ❌ 还超 2.5x
```

**v1.6 plan（已写未实施）的目标本身不达标**。需要新方向。

讨论中浮现 v2.5：**给 POI 数据预标"适合什么人群"，运行时按人群路由检索**。这一招同时打中：

| 维度 | 怎么帮 |
|---|---|
| 硬约束 **< 10s** | POI 池 ~800 → ~50，prompt token 砍 80%+，LLM 自然更快 |
| 完整性 / **多约束满足** | "人群"成为显式约束（之前只在 ranker 里隐式加权） |
| 创新性 / **体验创新** | 解锁"多方案对比"——同 query 给情侣 vs 家庭两套，对应赛题 D2"差异化方案" |
| 创新性 / **技术创新** | "离线 LLM 预标 + 运行时人群路由" 是亮点（不是 ReAct 但同样能讲故事） |
| 应用效果 / **可解释** | 每个 POI 推荐都能讲"为什么给你这个"——reviewTags + special 字段透明 |

---

## 2 · Goals / Non-Goals

### Goals

1. **POI 池砍小**：每次 search 召回从 ~800 砍到 ~20-50（按人群路由）
2. **个性化输出**：同 query 改 `traveler_type` → 路线明显不同
3. **可解释**：每个 POI 推荐有结构化字段支撑（reviewTags / special / 布尔标签）
4. **不破坏 95 测试基线**：所有改动向后兼容
5. **离线管道独立**：不堵主流程，标签数据 commit 进 git 队友共享

### Non-Goals (defer to v2.5.1+ or beyond)

- ❌ **多方案对比**（同 query 输出情侣版 + 家庭版两套）—— 后端近乎免费但前端要改，留 v2.5.1
- ❌ **真接口 reviewTags 适配**（hackathon 跑 mock 即可）
- ❌ **动态学习用户偏好**（v3 Adjuster 范畴）
- ❌ **多语言支持**
- ❌ **首屏 < 10s 完整路径**（这是 v1.6+v2.5 协作目标，v2.5 单独不保证）

## 3 · Design Decisions（来自 brainstorm 9 题）

| # | 决定 | 理由 |
|---|---|---|
| Q-1 | **Scope = 直接深入 v2.5 spec** | 一招打三家，ROI 高于单独 v1.6 性能优化 |
| Q-2 | **标方法 = 纯结构化字段映射**（修订 brainstorm 原 LLM batch 方案） | 看完真数据发现 reviewTags + special 已含强信号，LLM batch 不必要；省 $5-10 + 30 min |
| Q-3 | **画像 = traveler_type 主轴 + 4 二元修饰符** | 兼容现有 6 类 + 升表达力 + 故事好讲 |
| Q-4 | **修饰符 = `轻量体力` / `重文化` / `重美食` / `怕排队`** | 互相正交 + UGC 能抽 + Planner 有杠杆 + `怕排队` 对应赛题原话 |
| Q-5 | **信号抽取 = 结构化字段映射规则** | reviewTags / special / queueable / isBlackPearl 直接可用 |
| Q-6 | **跳过 LLM batch prompt** | Q-2 修订后用不上 |
| Q-7 | **运行时 = 二阶段 filter + ranker** | 池砍小 + 召回不过严 + 故事完整 |
| Q-8 | **兜底 = 渐进松绑** | 系统努力满足，不突兀回退 |
| Q-9 | **Profiler = LLM 抽 + 规则兜底** | LLM 主导 + 规则可解释 |

## 6 · Algorithms

### 6.1 离线打标（`scripts/label_pois.py`）

```python
def label_traveler_types(poi) -> list[str]:
    tags = {t['tag'] for t in poi.get('reviewTags', [])}
    spec = set(poi.get('special', []))
    types = []
    if '适合约会' in tags:                  types.append('情侣')
    if '亲子友好' in tags or '提供婴儿椅' in spec: types.append('家庭亲子')
    if '无障碍' in spec:                    types.append('银发')
    if '适合聚会' in tags or '可包间' in spec:    types.append('朋友团')
    if '包厢私密' in tags or '商务宴请' in tags:  types.append('商务')
    if not types: types = ['独行']  # 兜底
    return types

def label_modifiers(poi) -> dict[str, bool]:
    tags = {t['tag'] for t in poi.get('reviewTags', [])}
    spec = set(poi.get('special', []))
    return {
        '轻量体力': '提供婴儿椅' in spec or '无障碍' in spec or '亲子友好' in tags,
        '重文化': '老字号' in tags or '本地特色' in tags,
        '重美食': '菜品精致' in tags or '食材新鲜' in tags or poi.get('isBlackPearl') == 1,
        '怕排队': not poi.get('queueable', False) and '等位久' not in tags,
    }
```

### 6.2 Profiler 规则兜底（`agents/profiler.py`）

```python
KEYWORD_RULES = {
    '重文化': ['博物馆', '历史', '文化', '古迹', '陕博', '碑林'],
    '重美食': ['美食', '吃', '小吃', '网红店', '陕菜', '凉皮', '肉夹馍'],
    '怕排队': ['不想排队', '省时间', '怕等', '工作日'],
}

def _apply_modifier_defaults(intent: ParsedIntent):
    text = (intent.user_input or '').lower()
    # traveler_type 推断
    if intent.traveler_type in ('银发', '家庭亲子'):
        intent.modifiers.setdefault('轻量体力', True)
    # 关键词增强
    for mod, keywords in KEYWORD_RULES.items():
        if any(w in text for w in keywords):
            intent.modifiers[mod] = True
    # 未填默认 False
    for m in ('轻量体力', '重文化', '重美食', '怕排队'):
        intent.modifiers.setdefault(m, False)
```

### 6.3 Search 二阶段（`agents/tools.py`）

```python
def _filter_by_traveler_type(pois: list[POI], traveler_type: str) -> list[POI]:
    return [p for p in pois
            if p.persona_labels and traveler_type in p.persona_labels.traveler_types]

def _score(poi: POI, intent_modifiers: dict[str, bool]) -> int:
    if not poi.persona_labels: return 0
    s = 0
    for m, want in intent_modifiers.items():
        poi_has = poi.persona_labels.modifiers.get(m, False)
        if want and poi_has:     s += 2  # 你想要 + 它有 → 强加分
        elif want and not poi_has: s -= 1  # 你想要 + 它没 → 轻减分
        # want=False 一律 0（不奖不罚）
    return s

def _rank_by_modifiers(pois: list[POI], intent_modifiers: dict[str, bool]) -> list[POI]:
    return sorted(pois, key=lambda p: _score(p, intent_modifiers), reverse=True)
```

### 6.4 渐进松绑（`agents/tools.py`）

```python
NEIGHBOR_TYPES = {
    '银发': ['家庭亲子'],
    '家庭亲子': ['银发'],
    '商务': ['朋友团'],
    '朋友团': ['商务', '情侣'],
    '情侣': ['朋友团'],
    '独行': ['朋友团'],
}

# 修饰符松绑优先级（先松谁）。理由：轻量体力是生理约束最不能松；怕排队对应赛题
# 原话次之；重文化/重美食是偏好可以让步。松绑按本列表正序逐个去掉。
RELAX_ORDER = ['重美食', '重文化', '怕排队', '轻量体力']

def _progressive_relax(pois: list[POI], intent: ParsedIntent, min_size=8, top_n=20) -> list[POI]:
    # Stage 1: 按 RELAX_ORDER 逐个去掉 active 修饰符 (4→3→2→1→0)
    active = {m: v for m, v in intent.modifiers.items() if v}
    for mod_to_drop in RELAX_ORDER:
        if mod_to_drop in active:
            del active[mod_to_drop]
            candidates = _filter_by_traveler_type(pois, intent.traveler_type)
            candidates = _rank_by_modifiers(candidates, active)[:top_n]
            if len(candidates) >= min_size:
                return candidates

    # Stage 2: 扩到相邻 traveler_type
    for neighbor in NEIGHBOR_TYPES.get(intent.traveler_type, []):
        candidates = _filter_by_traveler_type(pois, neighbor)
        if len(candidates) >= min_size:
            return candidates[:top_n]

    # Stage 3: 退回全池（无 persona）
    return pois[:top_n]


# search_pois 入口（修改）
async def search_pois(client, intent: ParsedIntent, anchor: str, category: str, ...) -> list[POI]:
    pois = await client.search(...)  # 原召回逻辑

    candidates = _filter_by_traveler_type(pois, intent.traveler_type)
    candidates = _rank_by_modifiers(candidates, intent.modifiers)[:20]

    if len(candidates) < 8:
        candidates = _progressive_relax(pois, intent)

    return candidates
```

## 10 · Risks & Mitigations

| 风险 | 缓解 |
|---|---|
| mock reviewTags 是模板生成，可能信号同质化 | Task 1 末尾人工抽检 30 个，准确率 < 80% 立刻调规则重跑 |
| 真接口 reviewTags 字段格式可能不同 | hackathon demo 跑 mock，赛后再适配 |
| 渐进松绑可能在边界 case (刚好 7 vs 8 候选) 触发不一致 | filter/rank 都是确定性的，但召回边界依赖 mock 数据顺序；测试用断言"召回数 ≥ X" + "首位 POI 含期望字段" 而不是断言完整 POI 列表 |
| Planner LLM prompt 大改影响输出质量 | Task 4 后跑 5 个不同 query 人眼验收，发现退步立刻回滚 |
| 标签覆盖率不均（某类 traveler_type 在 POI 池占比过低） | Task 1 跑完按 city 输出每个 traveler_type 的 POI 占比；任一类占比 < 5% (即 800 POI 里少于 40 个) 时调规则补 |

## 11 · Acceptance Criteria（demo 时讲什么）

1. **个性化对比演示**：同 query "西安三天预算 6000"，分别 `带长辈小孩` 和 `带女朋友` → 两次输出的全部 POI 的 `openshopid` 集合的 Jaccard 系数 < 0.5（即超过半数 POI 不同）
2. **性能演示**：v2 baseline wallclock vs v2.5，至少快 30%
3. **可解释演示**：随便指一个推荐 POI 讲"为什么给你这个" —— "这家 reviewTags 含'亲子友好' + special 含'婴儿椅' → 标了家庭亲子 + 轻量体力，跟你抽出来的画像匹配"
4. **未达标 fallback 演示**：极端 query（"商务+西安+三天+轻量体力+重文化"）跑出仍有合理推荐 → 讲渐进松绑

## 12 · Out of Scope（v2.5.1+ 或更晚）

- 多方案对比（同 query 输出 2 套）—— 后端近乎免费但前端要改
- 真接口 reviewTags 适配
- LLM batch 标签（Q-2 已修订掉，看完真数据发现没必要）
- 用户偏好动态学习（v3 Adjuster 范畴）
- 标签置信度评分（PersonaLabels 字段加 `confidence: float`，目前是硬 bool）
- POI 池预热缓存
- 首屏 < 10s（这是 v1.6 + v2.5 协作目标，需要 per-day streaming）

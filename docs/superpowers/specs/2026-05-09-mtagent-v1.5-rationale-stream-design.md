## 1. Background

v1 跑通了流式 reveal——评委可以看到 chips → POI 卡片 → 时间轴三段动画。但**评委只能看到"是什么"，看不到"为什么这样选"**。Agent 的决策过程是黑盒。

赛题是「智能路线规划」，所有同质方案都会输出 POI 列表。胜负点在于：**用户能否信任 Agent 的判断，理解每一个选择背后的逻辑**。"挑了万象天地"和"考虑到你带 4 岁小孩，我挑了万象天地——商场避热、有亲子区、就近能吃饭"是天差地别的产品体验。

v1.5 的使命：**让 Planner 在每个关键决策点流式吐出短句理由**——anchor 选完一句、每天编排完一句。骨架硬编码（pure function 模板），LLM 润色留 v1.5.1。

## 2. Goals (v1.5 交付能力)

| # | 能力 | 验收点 |
|---|---|---|
| 1 | **anchors 阶段 rationale** | `_pick_anchors` 返回后流出 1 条 `planner.rationale`（stage="anchors"），文案 ≤80 字含至少 1 个 anchor 名 + 1 个 traveler/preference/budget 关键词 |
| 2 | **每日 compose rationale** | 每条 `planner.day_done` 之后流出 1 条 `planner.rationale`（stage="compose"，day_index 对应），文案 ≤80 字含 anchor 名 + 当日节奏说明 |
| 3 | **骨架 pure function** | `agents/rationale.py` 提供 2 个无副作用的纯函数，输入 ParsedIntent + 阶段产物，输出 dict |
| 4 | **前端 reveal 段显示 anchors rationale** | `stage-candidates` 下方插浅灰小字 `💭 ...`，与 chips 同生命周期 |
| 5 | **前端 day card 顶部显示 day rationale** | 每个 day card 在标题下方一行浅灰小字 `💭 ...`，整段 timeline 持久可见 |
| 6 | **单测覆盖** | rationale generator 5+ case（不同 traveler_type、preferences 组合）+ SSE 协议测试断言事件位置和字段 schema |

---

## 3. Non-Goals (v1.5.1 / v2 / v3 单独 spec)

- ❌ **LLM 润色层** —— v1.5.1 候选；本轮直出骨架文案，避免 demo 卡顿
- ❌ **cluster 阶段 rationale** —— 三阶段会噪音过大，cluster 信息已隐含在 day rationale 里
- ❌ **rationale 编辑/反馈** —— v3 反馈闭环范围
- ❌ **rationale 与 transit 时间联动** —— 等 v2 高德 API 接入后再加（"为什么不跨区"用 transit 数据是硬证据）
- ❌ **多语言** —— 仅中文
- ❌ **rationale 持久化** —— 不写入 TripContext，只是流式产物（v1.5 内不需要）

## 5. 数据契约

### 5.1 事件 schema

```jsonc
{
  "event": "planner.rationale",
  "data": {
    "stage": "anchors" | "compose",
    "day_index": null,           // anchors 阶段为 null，compose 阶段为 0..days-1
    "text": "考虑你带长辈和孩子，我挑了钟楼 / 大悦城两个片区——市中心地标 + 室内避热，避免郊区长途。",
    "key_factors": [             // 可选，调试与未来评估用
      "traveler_type=家庭亲子",
      "city=西安",
      "anchors=钟楼,大悦城"
    ]
  }
}
```

**字段约束：**
- `stage` —— 枚举两值
- `day_index` —— anchors 阶段必为 `null`；compose 阶段必为整数
- `text` —— 中文字符串，<=80 字（不严格校验，建议长度），不含 markdown / emoji（emoji 由前端加 `💭` 前缀）
- `key_factors` —— 字符串数组，每项 `key=value` 形式，调试 + 后期 eval 用

### 5.2 事件序列变化（v1 → v1.5）

```
trip.started
profiler.start
profiler.understood
profiler.ready
planner.start
planner.anchors
planner.rationale(stage=anchors)        ← NEW
planner.candidates_loaded
planner.clusters_ready
planner.compose_start
planner.day_done(0)
planner.rationale(stage=compose, day_index=0)   ← NEW
planner.day_done(1)
planner.rationale(stage=compose, day_index=1)   ← NEW
planner.day_done(2)
planner.rationale(stage=compose, day_index=2)   ← NEW
planner.done
critic.start
critic.done
trip.complete
```

3 天行程：v1 = 16 事件，v1.5 = 20 事件（+1 anchors + 3 day rationale）。

## 6. 骨架文案逻辑

### 6.1 `build_rationale_for_anchors(intent, anchors) -> dict`

**输入：**
- `intent: ParsedIntent` —— 含 traveler_type / preferences / budget_level / city / days / must_visit
- `anchors: list[tuple[str, float, float]]` —— `[(name, lat, lng), ...]`

**输出：** dict per §5.1（stage="anchors"，day_index=None）

**文案构造（确定性模板组合）：**

```
{traveler_phrase}{preference_phrase}，我挑了 {anchor_names}——{anchor_explanation}{budget_tail}。
```

各组件模板：
- `traveler_phrase`：
  - 情侣 → "考虑你们是情侣"
  - 家庭亲子 → "考虑你带孩子"
  - 银发 → "考虑你带长辈"
  - 独行 → "你一个人出行"
  - 商务 → "你出差行程紧"
  - 朋友团 → "考虑朋友团出行"
  - None → "结合你的偏好"
- `preference_phrase`：preferences 含 "拍照/打卡/出片" → "+爱拍照"；含 "美食" → "+爱吃"；含 "文化/历史" → "+喜欢人文"；空 → ""
- `anchor_names`：`" / ".join([a[0] for a in anchors])`，超 3 个截断为前 3 + "等"
- `anchor_explanation`：基于 traveler_type 兜底文案
  - 情侣 → "都是出片好地标 + 周边有氛围餐厅"
  - 家庭亲子 → "市中心地标 + 室内商场，避免郊区奔波"
  - 银发 → "节奏舒缓的人文地标"
  - 独行 → "灵活紧凑的城市核心区"
  - 商务 → "高铁/机场可达性强"
  - 朋友团 → "热闹氛围的核心商圈"
  - None → "城市的核心商圈"
- `budget_tail`：budget_level == "性价比" → "，控住人均预算" / "精致" → "，挑了品质感的去处" / "适中" 或 None → ""

**示例：**
- 输入：`traveler_type="家庭亲子"`, `preferences=["拍照"]`, `anchors=["钟楼", "大悦城"]`, `budget_level="性价比"`
- 输出：`"考虑你带孩子+爱拍照，我挑了 钟楼 / 大悦城——市中心地标 + 室内商场，避免郊区奔波，控住人均预算。"`

### 6.2 `build_rationale_for_day(intent, day_index, day_plan, anchor_name) -> dict`

**输入：**
- `intent: ParsedIntent`
- `day_index: int`
- `day_plan: DayPlan` —— 含 stops list（含每个 Stop 的 slot.name 和 poi.categories）
- `anchor_name: str` —— 对应的 anchor 名

**输出：** dict per §5.1（stage="compose"，day_index 填）

**文案构造：**

```
Day {day_index+1} 集中在 {anchor_name} 附近，{rhythm_phrase}。{traveler_tail}
```

各组件模板：
- `day_index+1` —— 1-based 显示
- `rhythm_phrase`：基于 stops 数和 slot 类型组合
  - stops >=4：`"上午 {stop0_slot}，中午就近 {lunch_stop_or_no}，下午 {pm_slot}"`
  - stops <=3：`"早午晚就近串成一线"`
  - 落到具体 slot 名：上午景点 / 午饭 / 下午茶 / 下午 / 晚饭 / 夜场
  - 用 stops 真实数据；若 stops 空（fallback 失败）→ "暂无可推荐节奏"
- `traveler_tail`：基于 traveler_type
  - 银发 → "节奏舒缓，避免长途奔波。"
  - 家庭亲子 → "尽量室内 + 短间距，方便带娃。"
  - 情侣 → "拍照点和氛围餐厅都安排上了。"
  - 独行 → "节奏紧凑，单点深度体验。"
  - 商务 → "效率优先，集中在交通核心。"
  - 朋友团 → "主打热闹氛围。"
  - None → ""

**示例：**
- 输入：`traveler_type="家庭亲子"`, `day_index=0`, anchor="钟楼", stops=[钟楼-上午景点, 回民街-午饭, 大悦城-下午]
- 输出：`"Day 1 集中在 钟楼 附近，上午 上午景点，中午就近 午饭，下午 下午。尽量室内 + 短间距，方便带娃。"`

注：rhythm_phrase 的 slot 名复用既有命名（"上午景点" / "下午" 不重复"景点"等冗余）；如要更自然要靠 v1.5.1 LLM 润色。

### 6.3 错误兜底

generator 不抛错。任何输入异常（intent 缺字段 / anchors 空 / day_plan stops 空）都走兜底文案：
- anchors 空 → `"我帮你看了城市核心区域。"`
- intent 缺关键字段 → 跳过对应 phrase 组件
- stops 空 → `"Day {i+1} 暂无可用编排。"`

## 7. 后端集成点

`api/routes.py::plan_stream` 改两处：

**改点 1：**`yield format_event("planner.anchors", ...)` 之后，紧跟：
```python
yield format_event(
    "planner.rationale",
    build_rationale_for_anchors(intent, anchors),
)
```

**改点 2：**循环 `for d in days_out:` 内 `yield planner.day_done` 之后，紧跟：
```python
yield format_event(
    "planner.rationale",
    build_rationale_for_day(
        intent,
        d.day_index,
        d,
        anchors[d.day_index][0] if d.day_index < len(anchors) else "",
    ),
)
```

**不动：** Planner 类内部、错误处理、其他 SSE 事件。这是外科手术式增量。

## 8. 前端集成点

`web/plan_stack.html::handleEvent` 加新 case：

```javascript
case "planner.rationale":
  if (data.stage === "anchors") {
    renderAnchorRationale(data.text);
  } else if (data.stage === "compose") {
    pendingDayRationales.set(data.day_index, data.text);
    // 若对应 day card 已 render，回填一次
    upsertDayRationale(data.day_index, data.text);
  }
  break;
```

辅助 render：

- `renderAnchorRationale(text)` —— 在 `stage-candidates` 下方插一个 `<div class="text-stone-500 text-sm italic mt-2">💭 ${text}</div>`
- `upsertDayRationale(dayIndex, text)` —— 找到 `[data-day="${dayIndex}"]`，在标题下面插浅灰小字。`renderDay` 也要从 `pendingDayRationales` 取一次（处理事件先后顺序）

**问题：rationale 事件可能在 day_done 之前到吗？** 不会——后端我们在 day_done 之后立刻 yield rationale，**且单线程顺序生成**。但保险起见 `renderDay` 也读一次 pending map。

**reveal-section 800ms hide 之后：** anchor rationale 会随 reveal 段消失，**这是预期**（anchors 是过程信息）。day rationale 在 timeline 永久保留。

## 11. 风险与回退

| 风险 | 应对 |
|---|---|
| 文案僵硬不像人说的 | v1.5.1 加 qwen-turbo 润色，本轮接受机械感（demo 时讲"骨架是确定的，可叠 LLM 润色"）。**v1.5 实测发现真实例子：** "Day 1 集中在 福田CBD 附近，上午 上午景点，中午就近 午饭，下午 下午" — slot 名重复拼接像填表没填完。v1.5.1 必修三件事：(a) 节奏 phrase 不直接复用 slot 名，按时间段+POI 类型组合；(b) 加硬证据（POI 名 / 通勤分钟 / 预算约束）；(c) 万能尾句"拍照点和氛围餐厅都安排上了"换成基于真实 stops 推导的具体话。 |
| stops 空时兜底文案破坏体验 | 直接用兜底文案 + 监控；任何 fallback 行为不抛 |
| 前端事件先后乱序 | render 用 pending map，day_done 与 rationale 先到都行 |
| 中文长度溢出 80 字 | 不严格校验，靠模板控制；超长不影响功能 |
| 用户人眼验收发现文案有 bug | TDD 已覆盖核心 case，bug 修单测 + 实现 |

## 12. 与 v2 / v3 的接口

- **v2 高德 API**：transit 时间填进 Stop 后，`build_rationale_for_day` 可 opt-in 读 `stop.transport_to_next_minutes`，加一句"两点间地铁 12 min"作为 rhythm_phrase 增强。**本轮不实现**，但函数签名要预留（`day_plan` 已含 stops，未来加字段不破坏接口）。
- **v3 Adjuster**：用户拒了某 POI 后，Adjuster 替换并触发 `planner.rationale` 复发（stage=compose 同 day_index）。前端 upsert 逻辑已预留。
- **v1.5.1 LLM 润色**：generator 输出后再走 qwen-turbo 一道，timeout 300ms 走骨架原文。事件 schema 不变。

## 1. Background

v1.5 全部交付后，切真 qwen3.6-plus（thinking off）跑端到端 36s，profile 时间分解：

| 阶段 | 耗时 | 占比 |
|---|---|---|
| Profiler LLM | 2.7s | 5% |
| 工具层（搜索 / 聚类 / 过滤 / 排序）| 0.06s | 0% |
| **Planner compose 单次 LLM call** | **48.7s** | **94%** |
| 其他 | <0.05s | 0% |

**问题：Planner 一次性大 prompt（候选 POI + 约束 + 要求输出 3 天 × 4 stops 的大 JSON），LLM 等返回 ~50s。期间 SSE 完全没事件，`compose_start` 之后死寂 50s 直到全部 `day_done` 一齐喷出。这是 demo 最大体感问题——不是慢，是「卡死然后突然出来」。**

用户原话："a 肯定要有一直能看到进展，结合 b 每天的内容分开三次输出。用户不会觉得等了 50s 而是 3 个十几秒，而且流式输出也会弱化用户在等待的一个想法。"

## 2. Goals (v1.6 交付能力)

| # | 能力 | 验收点 |
|---|---|---|
| 1 | **每天独立 LLM call** | Planner compose 拆成 N 次（N=days）调用，每次只编排一天，输入只含本日 anchor + 该日聚类的候选 POI |
| 2 | **每天调用并发执行** | N 次 LLM call 用 `asyncio.gather` 并发；最快的天先完成先 yield `day_done` |
| 3 | **字符级流式（每天内）** | 每次 LLM call 用 `stream=True`，能解析增量 JSON 时尽早 yield 中间事件（如 `planner.day_partial`），最终再 yield `planner.day_done` |
| 4 | **总耗时降到 15-20s** | 3 天并发 + 单天 ~15s = 用户感知 15-20s（vs v1.5 的 36-50s） |
| 5 | **每个 day_done 后仍走 v1.5 rationale** | 每完成一天，紧跟 `planner.rationale (stage=compose, day_index)` —— v1.5 协议保留 |
| 6 | **回退兼容** | LLM 单次 call 失败时降级到 v1.5 fallback synthesis（_synthesize_fallback_route），不破坏 v0/v1 既有契约 |
| 7 | **测试** | unit：拆分逻辑（按 day_index 分 prompt）；SSE 集成：N 个 day_done 仍按 day_index 顺序到达（asyncio.as_completed 处理乱序）|

## 5. 核心设计

### 5.1 单天编排 prompt 结构

每天独立 prompt 只送本日 anchor + 本日聚类后的 ranked POI list（5-15 个）：

```
你是行程编排助手。请为 {city} 第 {day_index+1} 天编排路线。

约束：
- anchor: {anchor_name}（lat, lng）
- traveler_type: {traveler_type}
- pace: {pace}
- budget_level: {budget_level}
- 当日 day template: {slots json}（如 上午景点 / 午饭 / 下午 / 晚饭）

候选 POI（仅本日 anchor 周边 5km 已聚类）：
{poi list with id/name/categories/star/avgprice/business_hour}

输出 JSON：
{
  "stops": [
    {"poi_openshopid": "...", "slot_name": "上午景点"},
    ...
  ]
}
```

vs v1.5 当前一次性大 prompt 含全部 N 天 anchor + N 个聚类的所有 POI + 大 JSON 输出格式。**单天 prompt token 数预估降到 1/3-1/4**，单次响应也更快（输出小）。

### 5.2 并发与有序 yield

```python
tasks = [compose_one_day(d, ...) for d in range(days)]
for coro in asyncio.as_completed(tasks):
    day_idx, day_plan = await coro
    yield format_event("planner.day_done", ...)
    yield format_event("planner.rationale", build_rationale_for_day(...))
```

**乱序问题：** `as_completed` 按完成时间顺序到，可能 Day 2 先完 Day 1 后完。前端已经用 `data-day` 索引 + `pendingDayRationales` map 处理了乱序，**v1.5 前端已就绪，不动**。

### 5.3 字符级流（stream=True）

LLM 一次 call 用 `stream=True`，OpenAI SDK 异步迭代器：

```python
async with client.chat.completions.stream(...) as stream:
    buf = ""
    async for chunk in stream:
        delta = chunk.choices[0].delta.content or ""
        buf += delta
        # 增量解析：当 buf 第一次能解析到 stops[0] 时 yield day_partial
```

**增量解析策略：** 逐 chunk 累加，每收到 `}` 尝试 `json.loads(buf + "]}")` —— 如果成功且 stops 列表长度增加，yield `planner.day_partial(day_index, stops_so_far)`。最终 buf 完整后 yield `planner.day_done`。

**前端 day_partial 处理：** 已有 `renderDay` 路径，只需补 case `planner.day_partial`：用最新 stops 复重 render（覆盖式更新 day card 内容）。

### 5.4 风险与回退

| 风险 | 应对 |
|---|---|
| LLM 单天调用失败 | 降级到 `_synthesize_fallback_route(templates[d:d+1], anchors[d:d+1], ranked_clusters[d:d+1], intent)` 单天合成 |
| 增量 JSON 解析复杂度高 | v1.6 第一版可不做 day_partial（只做拆分 + 并发），day_partial 留 v1.6.x |
| 跨天重复 POI | v1.6 接受；v1.6.1 加 visited_ids 黑名单 |
| 并发 N=3+ qwen 调用触发 dashscope 限流 | 加 `asyncio.Semaphore(3)` 限并发；retry 一次 |
| 前端事件乱序破坏渲染 | v1.5 已用 day_index map，已验证 |
